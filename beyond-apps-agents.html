Definition

Three moving parts. That is the whole thing.

An agent takes a goal, decides for itself what to do, and calls your functions to act—looping until the goal is met. You give it the goal. It works out the steps.

Component 1
Brain

A model that plans the next step.

Replaceable — you will swap it twice this year.

Component 2
Tools

Your Kotlin functions.

This part is yours, and nobody can copy it.

Component 3
Loop

Feed each result back and decide again.

This is the part that finishes the job.

Remove any one of the three and you do not have an agent. You have a chatbot with extra steps.

How it thinks

The whole idea, in seven lines.

Forget frameworks for a minute. This is all an agent runtime does. 

the agent loop step 1 of 6
var chat = listOf(userSaid(goal))

repeat(MAX_STEPS) {
  val reply = model.ask(chat, myTools)        // THINK
  if (reply.toolCall == null) return reply.text

  val result = runTool(reply.toolCall)        // ACT
  chat = chat + reply + result                // OBSERVE
}

That repetition is the entire difference between an agent and a single API call.

THINK

The model looks at the chat so far and picks one tool to call.

ACT

Your Kotlin function runs. The model never executes anything itself.

OBSERVE

The result is appended, and the model decides again.

Why repeat, not while

A wrong result can convince a model to retry forever. Always cap it.

Eleven lines. This agent can already answer questions your Reports screen needed five taps for.

How other agents refer to it. Keep it snake_case.

model

Swap this one line to go cloud, on-device, or hybrid.

instruction

A contract, not a personality. Say what must always happen.

tools

Generated from your @Tool functions by KSP. No JSON by hand.

Code

Running it is just a Flow.

KharchaViewModel.kt
val runner = InMemoryRunner(agent, sessionService)

fun ask(text: String) = viewModelScope.launch {
  runner.runAsync(userId, sessionId, message(text))
    .collect { event ->
      showOnScreen(event.text)
    }
}

If you know Flow and ViewModel, you already know how to run an agent.

Every step is an event

Tool calls, partial text, errors. Show them — a visible plan beats a spinner.

Sessions can persist

Swap InMemory for the Room-backed session service and the chat survives a restart.

Cancellation is free

viewModelScope stops the flow when the user leaves. No tokens billed for nothing.

Read this before you pick

Three backends. Not interchangeable.

Backend Runs Tool Calling Reach for it when
LiteRT-LM (Gemma) On device Yes You need a real agent that works offline
ML Kit (Gemini Nano) On device Not yet Summarise, rewrite, chat — no tools, still beta
Firebase AI (Gemini) Cloud Yes Best reasoning, and no secret key in your APK
Two traps worth writing down:

Plain Gemini can’t use an API key on Android — use Firebase AI. And Gemini Nano via ML Kit silently drops tool calls, so on-device tools means LiteRT-LM.

Every backend is the same LlmAgent. Switching is a one-line change — the capabilities are not.

The part nobody blogs about

So how do you ship a 2.5 GB model?

You cannot put it in the APK. These are your three real options.

1
Download on first use

What the ADK sample does, and the AI Edge Gallery too. Simple — but you now own the hosting, the retries, the storage and the updates.

Custom CDN Delivery
2
Play for On-device AI

The model becomes an AI pack that Play hosts, delivers and updates. Beta. Watch the caps: 1.5 GB per pack, 4 GB per app version.

Google Play Delivery
3
Pick a smaller model

Often the honest answer. A tighter model that fits the cap and does one narrow job beats a big one you cannot deliver.

Targeted Slim LLMs

Rule of thumb: if the feature must work offline, budget the model delivery in the same sprint as the agent. Teams forget, and the feature slips a release.

Where agents actually fail

Accuracy is a naming problem.

The model picks a tool from your description and nothing else. It cannot read the body. 

a coin flip on every turn ?
@Tool fun get(id: String): String
@Tool fun getData(type: String): String
@Tool fun fetchInfo(q: String): String

// No categories. No units.
// No date format. The model guesses.
something it can actually route ✓ routed
@Tool
fun getSpendByCategory(
  @Param("One of: food, travel, rent, bills")
  category: String,
  @Param("Start date, YYYY-MM-DD")
  from: String,
): SpendTotal

Write every tool description for a new teammate who joined this morning: list the allowed values, state the units, say what comes back. Two vague tools are worse than one good one.

Delete tools before you describe them. Five sharp tools beat twenty fuzzy ones.
